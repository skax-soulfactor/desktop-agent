# 지식베이스 UX 개선 설계

> **상태: M1~M3 구현 완료.** 아래 계획은 전부 코드에 반영되어 있다.
> 구현: `src/main/memory/{store,recall,extract}.ts`, `src/renderer/src/memory/*`
> 미구현으로 남긴 것: 6절 M3의 **LLM 정리 패스(모순 탐지·통합)** — 룰 기반으로 잡히지 않는 영역이라 별도 과제로 둔다.

현재 `src/renderer/src/memory/MemoryView.tsx`(79줄)는 "타입 필터 + 평면 리스트 + 펼치기/삭제"가 전부다.
기억이 20개를 넘어가는 순간 훑기도, 찾기도, 고치기도 불가능해진다. 이 문서는 그 원인과 개선 설계를 정리한다.

---

## 1. 진단 — 왜 관리가 어려운가

### 1.1 UI 결손

| # | 문제 | 근거 |
|---|---|---|
| 1 | **검색이 없다** | 전량 스크롤만 가능. 타입 필터 4개가 유일한 좁히기 수단 |
| 2 | **편집이 없다** | `memory:update` IPC는 존재하는데(`ipc.ts:103`) UI가 쓰지 않는다. 자동 추출이 만든 **틀린 기억을 고칠 방법이 삭제뿐** |
| 3 | **보관이 반쪽** | `memory:list`는 `listMemories(true)`로 보관본까지 반환(`ipc.ts:101`). 리스트에 섞여 나오고, 타입별 카운트에도 포함돼 **숫자가 실제 활성 기억 수와 다르다**. 보관/복구 버튼도 없다 |
| 4 | **태그가 죽어 있다** | 저장·표시만 되고 클릭·필터 불가. 특히 `공유제외` 태그는 원격 피어 응답에서 기억을 배제하는 **기능적 의미**(`recall.ts:10`)가 있는데 UI에 전혀 드러나지 않는다 |
| 5 | **근거 추적 불가** | `sourceSessionId`를 저장만 하고 노출하지 않는다. "이 기억 왜 생겼지?"를 확인할 수 없다 |
| 6 | **사용 신호 미노출** | `lastRecalledAt`이 있는데 화면에 없다. 한 번도 안 불려간 죽은 기억을 골라낼 수 없다 |
| 7 | **중복 대응 없음** | 추출 프롬프트가 중복 금지를 지시하지만(`extract.ts:36`) LLM이 제목 목록만 보고 판단한다. 유사 기억이 쌓이면 사용자가 손으로 찾아 지워야 한다 |
| 8 | **수동 추가 불가** | 사용자가 규칙을 직접 넣으려면 대화창에서 "기억해줘"를 해야 한다 |
| 9 | **본문이 평문** | `content`는 마크다운인데 `white-space: pre-wrap`로 렌더(`MemoryView.tsx:62`). lesson의 **상황/실수/원인/재발 방지** 구조가 시각적으로 무너진다 |
| 10 | **컨텍스트 비용 불가시** | 활성 기억 **전체의 제목 인덱스가 매 턴 프롬프트에 들어간다**(`recall.ts:21`). 기억이 늘수록 매 턴 비용이 늘어나는데 사용자는 이 사실을 알 수 없다 |

### 1.2 백엔드 함정 (개선 시 반드시 처리)

- **`searchMemories()`에 부수효과가 있다.** 내부에서 `markRecalled()`를 호출한다(`store.ts:90`).
  UI 검색이 이 함수를 그대로 쓰면 **사용자가 검색할 때마다 `lastRecalledAt`이 갱신돼** 회상 이력 지표가 통째로 오염된다.
  → 순수 조회 `queryMemories()`와 회상용 `recallMemories()`로 분리해야 한다.
- **`createMemory`가 `lastRecalledAt`을 생성 시각으로 채운다**(`store.ts:26`).
  생성은 회상이 아니다. 이 때문에 "한 번도 쓰인 적 없는 기억"과 "방금 쓰인 기억"이 구분되지 않는다.

## 2. 설계 원칙

1. **기억은 에이전트 자산이 아니라 사용자 자산이다.** 읽기·고치기·지우기가 대칭적으로 쉬워야 한다.
2. **목록이 아니라 작업대(workbench)다.** 훑기 → 찾기 → 고치기가 화면 전환 없이 한 곳에서 끝난다.
3. **자동 축적의 부작용을 UI가 선제적으로 드러낸다.** 중복·노후·형식 불일치를 사용자가 발견하게 두지 않는다.
4. **모든 기억은 출처와 사용 이력을 가진다.** 왜 생겼고 얼마나 쓰였는지 항상 확인 가능해야 한다.

### 3.1 요약 스트립

- 기존 `.usage-tiles` 스타일을 그대로 재사용(`styles.css:174`). 타일 클릭 = 해당 타입 필터.
- **보관 타일을 활성 카운트에서 분리** → 1.1의 #3 해결.
- **`⚠ 점검 필요` 뱃지**가 이 설계의 핵심. 클릭하면 점검 대기함(3.4)으로 필터링.
- **주입량 표시**: 활성 기억 제목 길이 합 기반 추정치. "기억이 늘면 매 턴 비용이 는다"는 사실을 사용자에게 처음으로 보여준다.

### 3.2 좌측 리스트

- 한 줄 = `체크박스 + 타입 칩 + 제목 + 마지막 회상 상대시간`. 밀도를 높여 40개를 한 화면에.
- **검색**: 제목·본문·태그 즉시 필터. 매칭 하이라이트는 기존 `.search-hit mark` 스타일 재사용(`styles.css:158`).
- **정렬**: 최근 갱신 / 최근 회상 / 오래된 순 / 회상 안 됨 순 / 타입별.
- **태그 클라우드**: 빈도 상위 태그를 칩으로. 클릭 = AND 필터. → 1.1의 #4 해결.
- **다중 선택 → 일괄 보관/삭제/태그 추가.** 자동 축적 시스템에서 정리는 항상 배치 작업이다.

### 3.3 우측 상세

- **마크다운 렌더** — 기존 `chat/Markdown.tsx`를 그대로 재사용. lesson 구조가 살아난다.
- **인라인 편집** — 제목·타입·태그·본문을 그 자리에서 수정하고 저장. `memory:update`가 이미 있으니 배선만 하면 된다. → 1.1의 #2 해결.
- **출처 대화 열기** — `sourceSessionId`로 대화 탭 점프. → 1.1의 #5 해결.
- **공유제외 토글** — 태그 문자열이 아니라 자물쇠 스위치로. 내부적으로는 `공유제외` 태그를 토글하되, 네트워크 탭에서 이 기억이 피어에게 나가지 않는다는 걸 UI로 설명한다.
- **메타 푸터** — 생성/갱신/마지막 회상/회상 횟수/출처.

### 3.4 점검 대기함 (Needs Review) — 가장 차별화되는 부분

자동 축적 시스템의 진짜 문제는 "많아서 안 보인다"가 아니라 **"틀린 게 섞여 있는데 어느 게 틀렸는지 모른다"**이다.
룰 기반으로 계산해 사용자에게 밀어준다(LLM 호출 없이 즉시 계산 가능):

| 신호 | 판정 | 제안 액션 |
|---|---|---|
| **중복 의심** | 같은 타입 내 제목·태그 토큰 자카드 유사도 ≥ 0.5 | "병합" — 한쪽 유지, 나머지 보관 |
| **노후** | 30일 이상 회상 0회 | "보관?" |
| **형식 불일치** | `type=lesson`인데 본문에 `재발 방지:` 섹션 없음 | "편집" |
| **출처 유실** | `sourceSessionId`에 해당하는 대화가 삭제됨 | "확인 후 유지/삭제" |
| **모순 의심** (v3) | 같은 태그·타입에서 내용 충돌 | LLM 정리 패스 |

각 항목에 **"확인함"** 버튼을 두고 `reviewedAt`을 찍어 대기함에서 내린다.

### 3.5 그 외

- **`+ 기억 추가`** — 사용자가 규칙을 직접 넣는 게 가장 확실한 통제 수단. `memory:create` IPC만 추가하면 된다.
- **채팅 ↔ 지식베이스 왕복** — 채팅의 `memory-saved` 카드에서 "지식베이스에서 보기" → 해당 항목 선택 상태로 이동. 역방향은 3.3의 출처 열기.
- **내보내기/가져오기** — `memories.json`을 마크다운 번들 또는 JSON으로. 백업·기기 이전·검토용.

## 4. 데이터 모델 변경 (하위호환, 전부 옵셔널)

```typescript
export interface MemoryEntry {
  // ... 기존 필드 유지
  /** 실제 회상 횟수. 0 = 저장 후 한 번도 쓰이지 않음 (노후 판정의 핵심 신호) */
  recallCount?: number
  /** 항상 컨텍스트에 주입할 핵심 기억 */
  pinned?: boolean
  /** 'agent' = 자동 추출, 'user' = 사용자가 직접 작성 (신뢰도 구분) */
  origin?: 'agent' | 'user'
  /** 사용자가 점검 대기함에서 확인 완료한 시각 */
  reviewedAt?: string
}
```

- 기존 항목은 필드 부재 → UI에서 "미확인"으로 표기. 마이그레이션 스크립트 불필요.
- **`createMemory`가 `lastRecalledAt`을 생성 시각으로 채우는 동작을 함께 고친다** (`store.ts:26`). 생성 시엔 비워 두고 `recallCount: 0`.

## 5. 백엔드 변경

### `src/main/memory/store.ts`

```typescript
queryMemories(opts)            // 순수 조회 — 부수효과 없음 (UI 검색/필터/정렬 전용)
recallMemories(query, topK)    // 기존 searchMemories = query + markRecalled + recallCount++
findDuplicates()               // 제목·태그 토큰 자카드 상위 쌍
mergeMemories(keepId, dropIds) // 유지본에 태그 합집합, 나머지 archived
memoryStats()                  // 타입별 개수, 보관 수, 주입 토큰 추정
needsReview()                  // 3.4 룰 판정 결과
```

`recall.ts`만 `recallMemories`를 쓰고, IPC는 전부 `queryMemories`를 쓴다. → 1.2의 부수효과 문제 차단.

### IPC 추가 (`ipc.ts` / `preload/index.ts` / `shared/api.ts` 동시 확장)

```
memory:create      memory:stats       memory:duplicates
memory:merge       memory:review      memory:bulk (archive|delete|tag)
memory:export      memory:import
```

`memory:list`는 활성/보관을 구분해 반환하도록 시그니처를 명확히 한다(현재 `true` 하드코딩).

### 컴포넌트 분해 (`src/renderer/src/memory/`)

```
MemoryView.tsx      # 레이아웃 + 상태(검색/필터/정렬/선택)
MemoryStats.tsx     # 요약 스트립
MemoryList.tsx      # 좌측 리스트 + 다중 선택
MemoryDetail.tsx    # 우측 상세 + 인라인 편집
MemoryReview.tsx    # 점검 대기함
useMemories.ts      # 로드/갱신/낙관적 업데이트 훅
```

## 6. 단계별 구현 계획

### M1 — 작업대 기본형 (효과 대비 비용 최고, 여기부터 권장)

검색 · 정렬 · 태그 필터 · 2단 레이아웃 · 마크다운 렌더 · **인라인 편집** · 보관/복구 분리 · `+ 기억 추가`

- 백엔드는 `memory:create` **하나만** 추가하면 된다. `memory:list`가 이미 전량을 반환하므로 검색·정렬·필터는 전부 렌더러에서 처리 가능.
- 여기까지만 해도 1.1의 #1~#4, #9가 해소된다.

### M2 — 관측과 정리

요약 스트립 · 점검 대기함(중복·노후·형식) · 다중 선택 일괄 처리 · 출처 대화 점프 · `recallCount`/`origin` 필드 · `searchMemories` 부수효과 분리

- 1.1의 #5~#7, #10 해소. 1.2의 두 함정도 여기서 정리.

### M3 — 고급

병합 UI · 내보내기/가져오기 · 고정(pin) · **컨텍스트 주입 미리보기**("이번 턴에 이 기억들이 들어갑니다") · LLM 정리 패스(모순 탐지·통합)

- 주입 미리보기는 에이전트가 왜 그렇게 답했는지를 사용자가 이해하게 만드는, 신뢰도 측면에서 가장 강력한 기능이다.
